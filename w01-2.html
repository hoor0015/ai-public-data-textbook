1주차 2회차. 첫 만남: VSCode와 Claude Code

최종 수정: 2026-09-03 · 이 교재는 학기 중에도 계속 업데이트됩니다

이 실습에서 하는 것

1회차에서 우리는 에이전트가 "행동하는 AI"라는 것을 개념으로 배웠다. 이번 회차에는 그 에이전트를 내 노트북에 실제로 들이고, 첫 일을 시켜 본다. 이 실습이 끝나면 다음이 갖추어진다.

  • 내 노트북에 설치된 VSCode와 Claude Code 확장
  • 한 학기 동안 쓸 작업 폴더 (공공데이터분석)와 그 안의 세 하위 폴더(data, 산출물, 메모), 그리고 README.md
  • 에이전트의 파일 수정 제안을 비교 화면에서 읽고, 한 번은 거부하고 한 번은 승인해 본 경험
  • 말로 정한 폴더 규칙이 같은 대화와 새 대화에서 어디까지 지켜지는지 관찰한 기록
  • 에이전트에게 지시해서 만든 첫 산출물 (우리 동네 소개 문서, 목차와 표 포함)과 검색 없이 쓴 비교판
  • 내가 아는 사실 다섯 가지로 문서를 시험한 대조표
  • "에이전트가 무엇을 하고 무엇을 못 하는지"를 정리한 표, 첫 관찰 기록, 오늘 입력한 지시문을 모은 대화 기록

오늘의 목표는 분석이 아니다. 도구와 낯을 트고, 지시하고 결과를 받는 감각을 손에 익히는 것이다. 서두를 필요 없다. 오늘 익힌 조작(폴더 열기, 대화창에 지시 입력, 결과 확인)은 앞으로 13주 내내 매주 반복된다. 새 도구를 처음 만나는 날에 권하는 태도가 하나 있다. 에이전트가 "무엇을 했다"고 말한 것과 화면에 실제로 생긴 것을 짝지어 보는 것이다. 이 짝짓기가 오늘의 모든 단계에 들어 있고, 다음 주(2주차)의 관찰 실습으로 그대로 이어진다.

2.1 VSCode 설치와 화면 구성

무엇을 왜 하는가. VSCode(Visual Studio Code)는 마이크로소프트가 만든 무료 편집기다. 1회차에서 말했듯, 우리는 VSCode를 코드 짜는 곳이 아니라 에이전트의 사무실로 쓴다. 사무실이 있어야 직원이 출근할 수 있으므로, 첫 단계는 VSCode를 설치하고 화면의 어느 구역이 무슨 일을 하는지 눈에 익히는 것이다. 이 단계에는 아직 에이전트가 없다. 그래서 오늘 유일하게 지시문 없이 손으로만 하는 단계다.

설치

공식 사이트(code.visualstudio.com)에서 "Download for Windows"를 눌러 설치 파일을 받고, 실행해서 기본 설정 그대로 "다음"을 눌러 설치를 마친다. 한 가지만 신경 쓰자. 설치 중 "추가 작업 선택" 화면이 나오면 "PATH에 추가" 항목이 체크되어 있는지 확인한다(기본값으로 체크되어 있다). 지금은 "체크되어 있으면 된다"만 기억하면 충분하다.

화면과 낯 익히기

VSCode를 처음 열면 영어 화면에 낯선 아이콘이 가득하다. 우리가 쓸 부분은 네 곳뿐이다. 그림 1-4가 그 네 구역을 한 화면에 그린 것이다.

그림 1-4를 읽는 법은 이렇다. 바깥의 큰 사각형이 VSCode 창 하나이고, 그 안이 ① 탐색기, ② 편집기, ③ 터미널, ④ Claude Code 패널의 네 구역으로 나뉜다. 각 구역 안에는 오늘 실제로 보게 될 내용을 미리 그려 두었다. 맨 아래 상자가 이 그림의 요지다. 학생이 주로 쓰는 곳은 ④(지시)·①(확인)·②(읽기)이고, 에이전트가 일하는 곳은 ③과 ②의 파일이다. 여기서 알 수 있는 것은 사람과 에이전트가 같은 창을 쓰되 맡은 구역이 다르다는 점이다. 오늘 하루 여러분의 손은 주로 오른쪽 패널에, 눈은 주로 왼쪽과 가운데에 가 있게 된다.

  • ① 탐색기(왼쪽): 맨 왼쪽 세로 막대(활동 막대)의 맨 위, 문서 두 장 겹친 아이콘을 누르면 열린다. 열어 둔 폴더의 파일 목록이 여기 보인다. 오늘 이 구역의 용도는 하나다. 에이전트가 "만들었다"고 한 파일이 실제로 있는지 확인하는 곳.
  • ② 편집기(가운데 위): 탐색기의 파일을 클릭하면 내용이 여기 열린다. 에이전트가 기존 파일을 고치면 고치기 전과 후를 나란히 비교하는 화면(diff)도 여기 나타난다.
  • ③ 터미널(가운데 아래): 컴퓨터에 문자로 명령을 내리는 창구다. 이 과목에서는 명령 실행을 에이전트에게 맡기므로 여러분이 직접 칠 일은 거의 없고, 에이전트가 여기서 일하는 모습과 출력 결과를 확인하는 창으로 쓰면 된다. 평소에는 접혀 있다가 에이전트가 명령을 실행하면 나타나며, 메뉴 View → Terminal로 직접 열어 볼 수도 있다. 이 창의 정체(셸)는 3주차에서 배운다.
  • ④ Claude Code 패널(오른쪽): 다음 단계에서 확장을 설치하면 생긴다. 지시를 입력하는 창, 에이전트가 어떤 도구를 썼는지 보여 주는 기록, 승인·거부 버튼이 모두 여기 있다.

표 1-2. VSCode 네 구역과 오늘의 용도

구역 위치 누가 쓰는가 오늘 할 일
① 탐색기 왼쪽 학생(확인) 에이전트가 만든 폴더·파일이 실제로 있는지 본다. 파일을 손으로 만들고 이름을 바꿔 본다
② 편집기 가운데 위 학생(읽기), 에이전트(쓰기) 파일 내용을 열어 읽고, 수정 비교 화면을 본다
③ 터미널 가운데 아래 에이전트(실행) 에이전트가 실행한 명령과 그 출력을 읽는다
④ Claude Code 패널 오른쪽 학생(지시·승인), 에이전트(보고) 지시를 입력하고, 도구 사용 기록을 읽고, 승인·거부를 누른다

예상되는 화면과 결과. 설치 직후 VSCode는 폴더가 열리지 않은 상태로 시작한다. 탐색기에는 "Open Folder" 버튼만 보이고, 편집기 자리에는 환영(Welcome) 페이지가 떠 있다. 터미널과 Claude Code 패널은 아직 보이지 않는다. 정상이다. 패널은 2.2에서, 폴더는 2.3에서 생긴다.

검증. 두 가지 조작을 해 본다. (1) 활동 막대의 탐색기 아이콘을 눌렀다가 다시 누르면 왼쪽 구역이 접혔다 펼쳐지는가. (2) 메뉴 View → Terminal을 눌러 아래쪽에 터미널 창이 나타나는가. 나타나면 아무것도 입력하지 말고 닫는다. 이 두 조작이 되면 화면 구성은 익힌 것이다.

왜 하필 VSCode인가?
Claude Code는 터미널 단독으로도, 다른 편집기에서도 쓸 수 있다. 그런데도 VSCode를 표준으로 삼는 이유는 세 가지다. 첫째, 무료이고 어느 운영체제에서나 같다. 둘째, 탐색기 덕분에 에이전트가 만들거나 고친 파일을 바로 눈으로 확인할 수 있다. 셋째, 에이전트가 파일을 고칠 때 무엇이 어떻게 바뀌는지 나란히 비교 화면(diff)으로 보여 주어, 우리 과목의 핵심 습관인 "검증"에 유리하다.
유의 · 한글 이름과 경로
작업 폴더 이름은 공공데이터분석처럼 한글이어도 된다. 이 교재는 일부러 한글 이름을 쓰며, 3주차에서 한글 폴더 이름 때문에 생기는 오류를 에이전트가 어떻게 넘기는지 관찰하게 된다. 다만 Windows 사용자 이름(C:\Users\ 아래 폴더 이름)이 한글이면 일부 도구가 경로를 제대로 읽지 못하는 경우가 있다. 오늘 실습에서는 문제가 되지 않으므로 지금 바꿀 필요는 없고, 3주차 환경 구축에서 오류가 나면 그때 다룬다.

2.2 Claude Code 확장 설치와 로그인

무엇을 왜 하는가. VSCode의 기능을 넓혀 주는 부가 프로그램을 확장(extension)이라 한다. Claude Code는 이 확장의 형태로 VSCode 안에 들어온다. 사무실에 직원이 출근하는 단계다. 설치와 로그인은 처음 한 번만 하면 되고, 끝나면 그림 1-4의 ④ 구역이 생긴다. 끝에서 첫 인사를 건네며, 에이전트의 말과 화면의 사실을 처음으로 나란히 놓아 본다.

확장 설치

활동 막대에서 네모 블록 아이콘(확장)을 누르고, 검색창에 "Claude Code"를 입력한다. 제작자가 Anthropic으로 표시된 것을 확인하고 "Install"을 누른다.

유의 · 비슷한 이름의 확장
검색 결과에는 이름에 "Claude"가 들어간 제3자 확장이 여럿 나온다. 반드시 제작자(Publisher)가 Anthropic인 것을 설치한다. 제3자 확장은 이 교재의 설명과 화면이 다르고, 계정 정보를 요구하는 경우 보안 위험도 있다.

로그인

설치가 끝나면 활동 막대에 Claude 아이콘이 생긴다. 아이콘을 눌러 나오는 안내에 따라 로그인하면 브라우저가 열리며 Claude 계정 인증을 요청한다. 수강 안내에 따라 만든 구독 계정으로 로그인하고 승인하면, VSCode로 돌아와 대화창이 활성화된다. 이 과정은 처음 한 번만 하면 된다.

로그인이 끝나면 Claude Code 패널이 열린다. 화면 한쪽에 세로로 붙어 나타나며, 그림 1-4에서는 오른쪽에 그렸다. 왼쪽에 열렸다면 그대로 써도 되고, 패널 제목 부분을 끌어다 오른쪽에 놓아 옮길 수도 있다. 패널을 한 번 훑어 두자. 맨 아래가 지시 입력칸이고, 위쪽에 새 대화 버튼과 이전 대화 목록 버튼이 있다. 아이콘 모양은 버전에 따라 다르므로 마우스를 올려 설명 풍선을 읽어 찾는다.

지시문 예시
"안녕. 너는 지금 어느 폴더에서 일하고 있어? 열려 있는 폴더가 없으면 없다고 말해 줘. 그리고 네가 할 수 있는 일을 다섯 가지만 한 줄씩 한국어로 알려 줘."

예상되는 에이전트의 행동과 결과. 에이전트가 짧게 답한다. 아직 폴더를 열지 않았으므로 "현재 열린 작업 폴더가 없다"고 하거나, VSCode가 기본으로 잡아 둔 어떤 경로(예: 사용자 홈 폴더)를 알려 줄 것이다. 이어서 파일 읽기와 쓰기, 명령 실행, 웹 검색, 코드 작성 같은 항목이 나열된다. 대화창에는 대략 다음과 비슷한 모양이 보인다.

● 현재 VSCode에 열려 있는 작업 폴더가 없습니다.
  폴더를 열면 그 안에서 파일을 읽고 쓸 수 있습니다.

  제가 할 수 있는 일:
  1. 폴더 안의 파일을 읽고 요약하기
  2. 새 파일과 폴더 만들기
  3. 터미널에서 명령을 실행하기
  4. 웹에서 자료를 검색하기
  5. 코드를 작성하고 실행하기

첫 대화에서 에이전트가 영어로 답하는 일이 흔하다. 지시문에 "한국어로"를 넣었는데도 영어가 섞여 나오면 "한국어로 다시 답해 줘"라고 한 번 더 말하면 된다.

검증. 확인할 것은 두 가지다. (1) 답이 한국어인가. (2) 에이전트가 말한 폴더가 화면의 사실과 맞는가. 지금은 아무 폴더도 열지 않았으므로 "없다"거나 홈 폴더를 말하는 답이 맞고, 탐색기에 "Open Folder" 버튼만 보이는 화면이 그 증거다. 에이전트가 나열한 다섯 가지는 자기소개이지 약속이 아니며, 무엇이 실제로 되는지는 2.9에서 시험한다.

2.3 첫 대화: 작업 폴더 열기, 파일 만들기, 지시하기

무엇을 왜 하는가. 에이전트는 "열어 둔 폴더" 안에서 일한다. 한 학기 동안 쓸 폴더를 하나 만들고, 그 안에 세 개의 하위 폴더를 에이전트에게 시켜 만든다. 세 폴더의 역할은 다르다. data에는 원본 데이터 파일을 두고 손대지 않는다. 산출물에는 에이전트가 만든 표·그림·보고서가 쌓인다. 메모에는 관찰일지나 계획서처럼 사람이 쓰는 문서를 둔다. 이렇게 나누는 이유는 3주차에서 원리로 배우고, 오늘은 나누어 두는 것으로 충분하다. 첫 지시의 목적은 폴더 세 개가 아니라, 지시 → 승인 요청 → 실행 → 보고 → 확인이라는 한 바퀴를 처음으로 돌아 보는 데 있다.

작업 폴더 만들기와 열기

바탕화면에 공공데이터분석이라는 폴더를 만들고, VSCode 메뉴에서 File → Open Folder로 그 폴더를 연다. "이 폴더의 작성자를 신뢰합니까?"라고 물으면 "예"를 선택한다. 이제 탐색기에 (아직 텅 빈) 폴더가 보인다.

앞으로 매 실습의 시작은 언제나 같다. VSCode를 열고 → 이 폴더를 열고 → Claude Code 패널을 연다.

첫 지시

대화창에 첫 지시를 입력해 보자.

지시문 예시
"안녕. 이 폴더는 한 학기 동안 공공데이터 분석 수업에 쓸 작업 폴더야. 폴더 안에 data, 산출물, 메모 세 개의 하위 폴더를 만들고, 폴더 맨 위에 README.md 파일을 만들어서 각 폴더의 용도를 두 줄씩 설명해 줘. 모든 설명은 한국어로."

예상되는 에이전트의 행동과 결과. 대화창에 에이전트의 작업 과정이 차례로 나타난다. 폴더를 만드는 명령을 실행하겠다며 승인을 요청하고, README.md를 쓰겠다며 다시 승인을 요청할 수 있다. 패널에는 대략 이런 순서로 기록이 쌓인다.

● 세 개의 하위 폴더와 README.md를 만들겠습니다.
  Bash(mkdir data 산출물 메모)            ← 승인 요청
● Write(README.md)                       ← 승인 요청
● 완료했습니다. data, 산출물, 메모 폴더와 README.md를 만들었고,
  README.md에 각 폴더의 용도를 두 줄씩 한국어로 적었습니다.

기록의 각 줄 앞에 붙은 영어 낱말은 에이전트가 쓴 도구의 이름이다. 오늘은 네 개만 알면 된다. Bash는 터미널에서 명령을 실행한 것, Write는 새 파일을 쓴 것, Read는 파일을 읽은 것, Edit는 있는 파일을 고친 것이다. 괄호 안은 그 대상이다. 이 네 낱말만 읽을 줄 알면 에이전트의 보고문을 읽기 전에 무엇을 했는지 알 수 있다. 도구 기록을 본격적으로 읽는 연습은 2주차에서 한다.

승인 요청에는 에이전트가 실행하려는 명령이나 만들려는 파일의 내용이 문자로 보인다. 읽고 나서 승인한다. 폴더 세 개를 만드는 명령(mkdir)은 위험할 것이 없으므로 승인하면 된다. 왜 에이전트가 사소한 일에도 묻는지, 어떤 요청은 거부해야 하는지는 2주차(권한 모드)에서 다룬다. 잠시 뒤 탐색기에 세 개의 폴더와 README.md가 나타나고, README.md는 대략 다음과 같은 모양이다.

# 공공데이터분석 작업 폴더

## data
분석에 쓸 원본 데이터 파일을 두는 곳이다.
원본은 고치지 않고 그대로 보관한다.

## 산출물
에이전트가 만든 표, 그림, 보고서를 저장하는 곳이다.
파일 이름에 만든 날짜나 주차를 넣어 구분한다.

## 메모
수업 중 관찰과 기록을 남기는 곳이다.
관찰일지, 계획서처럼 사람이 쓰는 문서를 둔다.

검증. 에이전트의 보고만 믿지 말고 눈으로 확인한다. 세 가지다. (1) 탐색기에서 폴더 세 개가 실제로 생겼고 이름이 지시한 그대로(data, 산출물, 메모)인가. (2) README.md를 클릭해 열어 보면 설명이 한국어로, 폴더마다 두 줄씩 적혀 있는가. (3) 부탁하지 않은 것이 덧붙지는 않았는가. 예를 들어 폴더 안에 이름이 점으로 시작하는 빈 파일이 생겼거나, README에 "사용법" 같은 절이 추가되어 있을 수 있다. 이 "보고 따로, 실물 확인 따로"가 우리 과목의 기본 동작이다.

에이전트가 틀리는 장면 1: 시킨 대로 되지 않았다

첫 지시가 그대로 이루어지지 않는 일은 드물지 않다. 실제로 자주 보이는 어긋남은 세 종류다. 폴더 이름을 output, notes처럼 영문으로 바꿔 만들거나, README의 설명이 어떤 폴더는 두 줄이고 어떤 폴더는 한 줄이거나, 설명 문장 일부가 영어로 남는 경우다. 이런 어긋남은 사고가 아니라 오늘의 관찰 재료다. 잡는 순서는 네 단계다.

  1. 틀림. 에이전트는 "각 폴더의 용도를 두 줄씩 적었다"고 보고했다.
  2. 검증에서 발견. README.md를 열어 세어 보니 메모 폴더의 설명이 한 줄뿐이다. 보고와 실물이 다르다.
  3. 재지시. 무엇이 어떻게 다른지 짚어서 다시 시킨다. 이때 "다른 부분은 바꾸지 마"를 붙인다. 에이전트는 고치라는 곳을 고치면서 다른 곳까지 손대는 경우가 있기 때문이다.
  4. 수정 확인. 고친 뒤 파일을 다시 열어 두 줄이 되었는지, 다른 절이 그대로인지 본다.
지시문 예시
"README.md에서 메모 폴더의 설명이 한 줄뿐이야. 두 줄로 채워 줘. data와 산출물 절을 포함해서 다른 부분은 한 글자도 바꾸지 마."

예상되는 에이전트의 행동과 결과. 에이전트가 README.md를 다시 읽고 메모 절에 한 줄을 더하는 수정을 제안한다. 이번에는 새 파일을 만드는 것이 아니라 있는 파일을 고치는 것이므로, 편집기에 고치기 전과 후를 나란히 비교하는 화면이 나타난다. 이 화면을 읽는 법은 바로 다음 단계(2.4)에서 익힌다.

검증. 승인한 뒤 README.md를 열어 메모 절이 두 줄인지, data와 산출물 절의 문장이 이전과 같은지 본다. 여러분의 README가 처음부터 지시대로 되어 있었다면 이 장면은 건너뛰어도 좋다. 다만 "이번에는 맞았다"는 것과 "확인하지 않아도 된다"는 것은 다르다는 점을 기억해 두자.

2.4 네 구역 돌아보기: 파일 읽기, 수정 제안, 승인과 거부

무엇을 왜 하는가. 그림 1-4의 네 구역을 한 번씩 손으로 다뤄 본다. 특히 익힐 것은 에이전트의 수정 제안을 보여 주는 비교 화면(diff)과 승인·거부 버튼이다. 승인만 눌러 본 사람은 거부가 무엇을 막는지 모른다. 그래서 오늘은 같은 수정 제안을 일부러 한 번 거부하고 한 번 승인해서, 거부하면 파일이 그대로이고 승인하면 바뀐다는 사실을 눈으로 확인한다. 이 감각이 있어야 앞으로 에이전트가 데이터 파일이나 코드를 고치겠다고 할 때 안심하고 읽고 판단할 수 있다.

손으로: 탐색기에서 파일 만들기와 이름 바꾸기

먼저 에이전트 없이 파일 하나를 손으로 만든다. 탐색기에서 메모 폴더에 마우스 오른쪽 버튼을 누르고 "New File"을 고른 뒤 연습.md라고 입력하면 편집기에 빈 파일이 열린다. 첫 줄에 "오늘 VSCode를 처음 열었다."라고 적고 Ctrl+S로 저장한다. 이어서 파일 이름 위에서 오른쪽 버튼을 눌러 "Rename"을 고르고(단축키 F2) 연습_1주차.md로 바꾼다. 손으로 만들어 보는 이유는 하나다. 에이전트가 만드는 파일과 여러분이 만드는 파일이 같은 종류의 물건임을 확인하는 것이다.

에이전트에게: 읽고, 요약하고, 수정을 제안하게 하기

지시문 예시
"README.md와 메모 폴더의 연습_1주차.md를 읽고 각각 한 줄로 요약해 줘. 그다음 README.md의 메모 폴더 설명 끝에 '관찰일지는 관찰일지_N주차.md 형식으로 저장한다.'라는 한 줄을 덧붙이는 수정을 제안해 줘. 내가 승인하기 전에는 파일을 바꾸지 마."

예상되는 에이전트의 행동과 결과. 패널의 도구 사용 기록에 파일 읽기가 두 번 나타나고, 요약 두 줄이 이어진다. 그다음 README.md를 고치겠다는 제안이 뜨면서 편집기 구역에 비교 화면이 열린다. 비교 화면은 대략 다음과 같은 모양이다. 새로 들어가는 줄에 더하기 기호(+)와 초록 배경이 붙는다.

  ## 메모
  수업 중 관찰과 기록을 남기는 곳이다.
  관찰일지, 계획서처럼 사람이 쓰는 문서를 둔다.
+ 관찰일지는 관찰일지_N주차.md 형식으로 저장한다.

패널에는 이 수정을 받아들일지 묻는 승인·거부 버튼이 나타난다. 여기서 두 번에 나누어 한다.

첫 번째는 거부한다. 거부를 누르면 에이전트가 "수정을 적용하지 않았다"는 취지로 짧게 보고한다. 탐색기에서 README.md를 열어 본다. 메모 절은 두 줄 그대로다. 거부는 제안을 없던 일로 만든다.

두 번째는 승인한다. "방금 제안한 수정을 다시 해 줘"라고 말하면 같은 비교 화면이 다시 뜬다. 이번에는 내용을 읽고 승인한다. 편집기의 README.md에 새 줄이 들어간다.

터미널 구역: 에이전트가 실행한 명령 읽기

지시문 예시
"터미널에서 이 폴더 안의 폴더와 파일 목록을 출력해서 보여 줘. 결과를 요약하지 말고 터미널에 찍힌 그대로 알려 줘."

예상되는 에이전트의 행동과 결과. 목록을 출력하는 명령(Windows의 PowerShell에서는 Get-ChildItem 또는 dir)의 실행 승인을 요청하고, 승인하면 아래쪽 터미널 구역이 열리면서 출력이 찍힌다. 날짜와 시각, 파일 크기는 각자 다르다.

    디렉터리: C:\Users\<사용자 이름>\Desktop\공공데이터분석

Mode                 LastWriteTime         Length Name
----                 -------------         ------ ----
d-----      2026-09-03   오후 2:10                data
d-----      2026-09-03   오후 2:10                메모
d-----      2026-09-03   오후 2:10                산출물
-a----      2026-09-03   오후 2:31            380 README.md

맨 앞의 d는 폴더(directory), -a로 시작하는 줄은 파일이다. 지금은 이 정도만 읽을 수 있으면 된다. 명령 자체를 읽는 법은 3주차에서 배운다.

검증. 세 구역을 대조한다. 터미널에 찍힌 목록, 탐색기에 보이는 목록, 에이전트가 패널에 보고한 목록이 서로 같은가. 세 곳이 같은 것을 가리키면 오늘의 화면 지도가 완성된 것이다. 하나라도 다르다면(예: 터미널에는 있는데 탐색기에 안 보인다) 탐색기 위쪽의 새로고침 아이콘을 눌러 본다.

대화 기록 구역: 지나간 대화 다시 열기

마지막으로 패널 위쪽의 이전 대화 목록 버튼을 눌러 본다. 오늘 나눈 대화가 시간 순으로 저장되어 있고, 하나를 고르면 그 대화로 돌아갈 수 있다. 새 대화 버튼을 눌러 새 대화를 열어도 이전 대화는 목록에 그대로 남는다. 이 기능은 2.5의 규칙 실험과 2.9의 첫 시험에서 바로 쓴다.

정의 · 비교 화면(diff)과 승인 요청
비교 화면(diff)은 파일의 고치기 전과 후를 줄 단위로 나란히 보여 주는 화면이다. 지워지는 줄은 빼기 기호와 붉은색, 새로 들어가는 줄은 더하기 기호와 초록색으로 표시된다. 에이전트가 기존 파일을 고칠 때마다 나타나며, 새 파일을 만들 때는 비교할 이전 내용이 없으므로 나타나지 않는다.
승인 요청은 에이전트가 파일을 바꾸거나 명령을 실행하기 전에 "이렇게 해도 되는가"를 사람에게 묻는 절차다. 승인하면 실행되고, 거부하면 아무것도 바뀌지 않는다. 승인 요청은 에이전트가 지금 무엇을 하려는지 알려 주는 창이기도 하다. 요청의 종류와 범위를 조절하는 방법(권한 모드)은 2주차에서 배운다.

2.5 말로 정한 규칙은 어디까지 지켜지는가: 폴더 규칙 실험

무엇을 왜 하는가. 2.3에서 폴더 세 개를 만들었지만 폴더는 아직 그릇일 뿐이다. 어느 파일이 어느 그릇에 들어가는지는 정해지지 않았다. 이번 단계에서는 그 규칙을 말로 정해 주고, 그 규칙이 어디까지 지켜지는지 관찰한다. 관찰의 결과는 "지킨다"와 "안 지킨다" 둘 중 하나가 아니다. 같은 대화의 바로 다음 지시에서는 대개 잘 지켜지고, 지시가 몇 번 오간 뒤에는 흐려지며, 새 대화에서는 아예 사라진다. 이 세 구간을 각자의 화면에서 확인해 두면, 2주차에 배울 CLAUDE.md가 왜 필요한지를 설명을 듣기 전에 알게 된다. 오늘은 일부러 규칙을 파일로 고정하지 않고 말로만 정한다. 말로만 정했을 때 무슨 일이 생기는지가 오늘의 관찰 대상이기 때문이다.

규칙 네 가지 정해 주기

지시문 예시
"지금부터 이 폴더에서 지킬 규칙 네 가지를 정할게. (1) data 폴더에는 내가 넣은 원본 데이터 파일만 둔다. 너는 data 폴더 안에 파일을 만들지 않는다. (2) 네가 만든 표, 그림, 보고서는 산출물 폴더에 넣는다. (3) 사람이 쓰거나 읽는 메모, 일지, 계획서는 메모 폴더에 넣는다. (4) 파일을 만들거나 고칠 때마다 보고의 마지막 줄에 '만든 파일: 전체 경로' 형식으로 한 줄을 적는다. 지금은 파일을 만들지 말고, 이 네 규칙을 네 말로 다시 정리해서 보여 줘. 규칙만으로는 판단이 어려운 경우가 있으면 그것도 함께 물어봐."

예상되는 에이전트의 행동과 결과. 이 지시에는 만들 파일이 없다. 그래서 승인 요청도, 도구 사용 기록도 나타나지 않고 대화창에 정리된 문장만 돌아온다.

● 규칙을 다음과 같이 이해했습니다.
  1. data 폴더: 사용자가 넣은 원본 데이터만 둡니다. 제가 파일을 만들지 않습니다.
  2. 산출물 폴더: 제가 만든 표, 그림, 보고서를 넣습니다.
  3. 메모 폴더: 사람이 쓰거나 읽는 메모, 일지, 계획서를 넣습니다.
  4. 파일을 만들거나 고친 뒤 보고의 마지막 줄에 전체 경로를 한 줄 적습니다.

  한 가지 확인하고 싶습니다. 제가 초안을 쓰고 사용자가 이어서 고치는
  관찰일지는 2번과 3번 중 어디에 넣을까요?

이런 되물음이 오면 그 자리에서 답을 정해 준다. "사람이 이어서 고치는 문서는 메모 폴더"라고 한 줄로 답하면 규칙이 사실상 다섯 개가 된 셈이다. 되묻지 않고 정리만 해 주는 경우도 많다. 어느 쪽이든 다음으로 넘어간다. 정리된 내용이 여러분이 말한 것과 다르면(예: 규칙 4를 "필요할 때 경로를 적는다"로 바꿔 적었다면) 지금 고쳐 둔다. 규칙을 어겼는지 판정하려면 규칙의 문장이 먼저 분명해야 한다.

검증. 이 단계에서 확인할 것은 화면에 아무 변화가 없다는 사실이다. 탐색기를 보라. 새 파일도 새 폴더도 생기지 않았어야 한다. "파일을 만들지 말고 정리만 해 줘"라고 했는데 규칙을 적은 파일이 생겼다면, 그것이 오늘의 관찰거리 하나다. 지시의 "하라"는 부분만이 아니라 "하지 마라"는 부분이 지켜지는지도 앞으로 계속 볼 지점이다.

갈래 1. 같은 대화의 바로 다음 지시

지시문 예시
"산출물 폴더의 용도에 맞는 파일 하나를 만들어 줘. 이름은 '폴더구조.md'고, 우리 작업 폴더의 구조를 '폴더 이름·용도·지금 들어 있는 파일 수' 세 열의 표로 정리한 문서야. 파일 수는 짐작하지 말고 폴더를 실제로 확인해서 적어. 방금 정한 규칙 네 가지를 지켜."

예상되는 에이전트의 행동과 결과. 규칙을 정한 직후이므로 대개 그대로 지켜진다. 폴더 안을 확인하는 명령을 한 번 실행하고, 산출물 폴더에 파일을 쓰고, 마지막 줄에 경로를 적는 순서다.

● 폴더 안을 먼저 확인하겠습니다.
  Bash(dir /s /b)                                  ← 승인 요청
● Write(산출물\폴더구조.md)                        ← 승인 요청
● 폴더구조.md를 만들었습니다. 현재 data 폴더는 비어 있고,
  메모 폴더에 1개, 산출물 폴더에 1개의 파일이 있습니다.
  만든 파일: C:\Users\<사용자 이름>\Desktop\공공데이터분석\산출물\폴더구조.md

검증. 세 가지를 본다. (1) 탐색기에서 폴더구조.md가 산출물 폴더 안에 있는가. 폴더 맨 위나 메모 폴더에 있다면 규칙 2를 어긴 것이다. (2) 보고의 마지막 줄에 전체 경로가 한 줄로 적혀 있는가. 규칙 4는 네 규칙 중 가장 자주 빠진다. 파일은 제자리에 만들면서 보고 형식만 잊는 일이 흔하다. (3) 표의 "파일 수"가 탐색기에서 직접 세어 본 수와 같은가. 여기서 수가 어긋난다면 에이전트가 폴더를 확인하지 않고 짐작으로 적은 것이다. 도구 사용 기록에 폴더를 확인하는 명령이 있었는지 함께 본다. 세 확인의 결과를 각자 적어 둔다. 과제 1-D의 첫 행이 된다.

갈래 2. 지시가 몇 번 오간 뒤

규칙을 정한 직후가 아니라, 다른 일을 몇 번 시킨 뒤에 다시 시험한다. 사이에 넣을 일은 규칙과 상관없는 것이면 무엇이든 좋다. README.md를 한 문단으로 요약하게 하고, 마크다운에서 표를 쓰는 문법을 설명하게 하고, 오늘 날짜를 요일까지 알려 달라고 하는 식으로 서너 번을 채운다. 그다음 아래를 입력한다.

지시문 예시
"오늘 실습에서 관찰한 것을 적을 '오늘의관찰.md'를 만들어 줘. 항목은 '잘된 것·안 된 것·다음에 시켜 볼 것' 세 개고, 내용은 내가 손으로 채울 테니 비워 둬."

이 지시문에는 폴더 이름이 없다. 일부러 뺐다. 규칙을 기억하고 있다면 사람이 쓰는 문서이므로 메모 폴더에 만들어야 하고, 규칙 4에 따라 경로 한 줄이 붙어야 한다. 폴더 이름을 적어 주면 규칙을 기억하는지가 아니라 지시를 따르는지를 보게 되므로 시험이 되지 않는다.

예상되는 에이전트의 행동과 결과. 결과는 대체로 셋 중 하나로 갈린다. 규칙대로 메모 폴더에 만들고 경로까지 보고하는 경우, 폴더는 맞게 골랐는데 경로 한 줄이 빠지는 경우, 폴더 맨 위나 산출물 폴더에 만드는 경우다. 세 번째가 나오면 화면은 대략 이렇게 보인다.

● Write(오늘의관찰.md)                             ← 승인 요청
● 오늘의관찰.md를 만들었습니다. 세 항목의 제목만 넣고
  내용은 비워 두었습니다.

보고에 폴더 이름이 없고 경로 줄도 없다. 승인 요청 창의 파일 이름에 폴더가 붙어 있지 않다는 점도 단서다. 앞의 갈래 1에서는 산출물\폴더구조.md처럼 폴더가 함께 보였다.

검증. 탐색기에서 오늘의관찰.md가 어느 폴더에 생겼는지 확인하고, 보고의 마지막 줄을 다시 읽는다. 파일이 폴더 맨 위에 있다면 규칙 3을, 경로 줄이 없다면 규칙 4를 어긴 것이다. 어긴 규칙이 있으면 번호를 짚어 재지시한다.

지시문 예시
"방금 만든 오늘의관찰.md는 규칙 3을 어겼어. 사람이 쓰는 문서니까 메모 폴더에 있어야 해. 파일을 메모 폴더로 옮기고, 규칙 4대로 옮긴 뒤의 전체 경로를 마지막 줄에 적어 줘. 파일 내용은 바꾸지 말고, 옮기기 전 위치에 파일이 남아 있지 않은지도 확인해 줘."

파일을 옮기는 작업에는 원래 자리의 파일을 지우는 일이 따라온다. 그래서 이 재지시에는 삭제 승인 요청이 함께 올 수 있다. 승인 창에 적힌 대상 파일의 이름과 폴더를 읽고, 방금 잘못 만들어진 그 파일이 맞을 때만 승인한다. 이름이 다르거나 여러 파일을 한꺼번에 지우는 명령이면 거부하고 하나씩 다시 시킨다.

갈래 3. 새 대화

패널 위쪽의 새 대화 버튼을 눌러 대화를 새로 연다. 폴더는 그대로 열려 있고 파일도 그대로지만, 지금까지 나눈 말은 이 대화에 없다.

지시문 예시
"우리 작업 폴더의 구조를 표로 정리한 파일을 하나 더 만들어 줘. 이름은 '폴더구조_2.md'야. 저장 위치는 아까 정한 규칙대로 하고, 규칙 4도 지켜 줘."

예상되는 에이전트의 행동과 결과. 두 갈래가 있다. 하나는 규칙을 모른다고 되묻는 것이다.

● 말씀하신 "아까 정한 규칙"의 내용을 제가 가지고 있지 않습니다.
  이 대화는 방금 시작되었습니다. 규칙을 다시 알려 주시겠습니까?

이것이 정직한 반응이다. 다른 하나는 되묻지 않고 그럴듯하게 짐작해서 만드는 것이다.

● 규칙에 따라 작업 폴더 맨 위에 정리하겠습니다.
  Write(폴더구조_2.md)                             ← 승인 요청
● 폴더구조_2.md를 만들었습니다.

"규칙에 따라"라는 말이 붙어 있지만 그 규칙이 무엇인지는 어디에도 없다. 파일은 폴더 맨 위에 생기고 경로 보고 줄도 없다. 다만 폴더 맨 위에 있는 README.md나 폴더 이름을 읽고 산출물 폴더를 골라 맞히는 경우도 있다. 맞혔더라도 그것은 규칙을 기억한 것이 아니라 눈앞의 파일을 보고 추측한 것이다.

에이전트가 틀리는 장면 2: 새 대화는 아까의 약속을 모른다

앞의 갈래 3에서 두 번째 반응이 나왔다면 그것이 오늘의 두 번째 틀리는 장면이다. 잡는 순서는 앞과 같다.

  1. 틀림. 에이전트가 "규칙에 따라" 파일을 만들었다고 보고했다. 그러나 이 대화에는 규칙이 전달된 적이 없다.
  2. 검증에서 발견. 탐색기를 보니 폴더구조_2.md가 산출물 폴더가 아니라 폴더 맨 위에 있다. 보고에 경로 줄도 없다. 규칙 2와 4가 함께 어긋났다.
  3. 재지시. 규칙을 다시 말해 주고 고치게 한다. "이 대화에는 규칙을 말한 적이 없어. 규칙은 이렇다. (네 규칙을 다시 붙여 넣는다) 폴더구조_2.md를 규칙에 맞는 폴더로 옮기고 경로를 마지막 줄에 적어 줘."
  4. 수정 확인. 탐색기에서 파일이 산출물 폴더로 옮겨졌는지, 폴더 맨 위에 남아 있지 않은지 확인한다.

여기서 중요한 것은 에이전트를 탓하는 대목이 아니다. 규칙을 매번 말로 다시 붙여 넣는 이 번거로움이 문제의 본체다. 대화를 새로 열 때마다 네 줄을 다시 치는 일이 한 학기 동안 반복된다면 언젠가는 빠뜨린다. 규칙을 사람의 기억이 아니라 파일에 적어 두고 에이전트가 매번 읽게 하는 방법이 2주차의 CLAUDE.md다. 오늘은 그 파일을 만들지 않는다. 없을 때의 불편을 먼저 겪어 두는 것이 오늘의 몫이다.

유의 · 어긴 결과를 지우지 말 것
규칙을 어겨 엉뚱한 자리에 만들어진 파일은 오늘의 증거물이다. 재지시로 제자리에 옮긴 뒤에도 어떤 파일이 어디에 잘못 생겼는지를 과제 1-D의 표에 적어 두어야 한다. 2주차에 CLAUDE.md를 만들고 같은 실험을 다시 하면, 오늘의 표와 그날의 표를 나란히 놓고 무엇이 달라졌는지 보게 된다. 그러니 오늘 만들어진 파일은 하나도 지우지 말고 그대로 둔다.

세 갈래의 결과 적어 두기

세 갈래의 관찰을 한자리에 모은다. 이 표는 에이전트에게 시키지 말고 손으로 채운다. 규칙을 어긴 당사자에게 어겼는지 물으면, 실제 파일이 아니라 자기 보고를 근거로 답할 수 있기 때문이다. 메모 폴더에 규칙실험_1주차.md를 만들고 아래 틀을 옮겨 적은 뒤, 칸마다 지켜졌는지와 그것을 무엇으로 확인했는지를 함께 쓴다.

왜 말로 한 규칙은 사라지는가?
에이전트는 대화 하나를 통째로 다시 읽으면서 다음 답을 만든다. 그래서 방금 정한 규칙은 잘 지켜진다. 그런데 대화가 길어지면 읽어야 할 양이 늘고, 앞쪽의 말은 뒤로 밀린다. 새 대화를 열면 읽을 것 자체가 없어진다. 이 성질을 다루는 이름과 원리(맥락창)는 2주차 1회차에서 배우고, 규칙을 파일에 적어 매번 읽히는 방법(CLAUDE.md)은 2주차 2회차에서 만든다. 오늘 여러분이 확인한 것은 그 설명을 듣기 전의 관찰 자료다. 관찰이 먼저 있고 이름이 나중에 붙는 순서가 이 교재의 방식이다.

2.6 미니 실습: 에이전트로 "우리 동네 소개 문서" 만들기

무엇을 왜 하는가. 이제 조금 더 실질적인 일을 시켜 보자. 자기가 사는(또는 잘 아는) 시군구를 하나 골라, 그 지역을 소개하는 문서를 에이전트와 함께 만든다. 주제를 "우리 동네"로 잡은 이유가 있다. 여러분이 이미 사실을 아는 대상이어야, 에이전트의 서술이 맞는지 여러분 스스로 판정할 수 있기 때문이다. 오늘은 두 판을 만든다. 1판은 세 항목을 조사해 출처와 함께 적은 문서이고, 2판은 거기에 목차와 표를 더한 문서다.

1판: 세 항목과 출처

지시문 예시
"메모 폴더에 '우리동네.md' 파일을 만들어 줘. 주제는 ○○시 ○○구(각자 선택)야. 웹을 검색해서 다음 세 가지를 조사해 담아 줘. (1) 인구 규모와 최근 증감 경향, (2) 행정동 개수, (3) 이 지역의 대표적인 행정 이슈 한 가지. 각 항목마다 정보의 출처(사이트 이름과 주소)를 반드시 함께 적어 줘. 확인되지 않는 내용은 지어내지 말고 '확인 불가'라고 적어."

예상되는 에이전트의 행동과 결과. 에이전트가 웹 검색 도구를 사용하는 과정이 대화창에 보인다. 검색어를 넣어 결과 목록을 받고, 그중 몇 페이지를 열어 읽는 기록이 몇 차례 반복된 뒤, 파일을 쓰겠다는 승인 요청이 온다. 웹 검색과 페이지 열람도 승인을 요구할 수 있다. 완성된 우리동네.md는 대략 다음과 같은 모양이다.

# ○○구 소개

최근 몇 년간 ... 경향을 보인다.

...

검증. 문서가 열리면 다음을 확인한다.

  1. 출처가 항목마다 실제로 붙어 있는가. 출처 없는 단정이 있다면 그 부분을 지적하고 고치게 하라. ("두 번째 항목에 출처가 없어. 출처를 찾아 붙이고, 못 찾으면 확인 불가로 바꿔 줘.")
  2. 출처 링크를 하나 골라 브라우저에서 직접 열어 보라. 정말 그 내용이 있는가. 인구 수치가 문서의 수치와 일치하는가.
  3. 수치의 기준 시점이 적혀 있는가. "인구 45만 명"은 언제 기준인가.
  4. 에이전트에게 같은 대화에서 재검산을 시켜 보라. "문서의 세 항목 각각에 대해 출처 페이지를 다시 열어서 문서의 서술과 일치하는지 대조하고, 항목·문서의 서술·출처 페이지의 서술·일치 여부 네 열의 표로 보여 줘." 이 표에서 "불일치"가 나오는 항목이 있으면 그것이 오늘의 수확이다.

여기서 1회차의 개념이 그대로 손에 잡힌다. 지시(원하는 항목과 형식, 지어내지 말라는 제약을 명시) → 에이전트의 실행(검색·작성) → 검증(출처 대조). 특히 "지어내지 말고 확인 불가라고 적어"라는 한 줄이 답을 검증 가능하게 만드는 실전 장치다(2주차에서 검증 손잡이라는 이름으로 배운다). 위 검증 4번처럼 검증 자체를 에이전트에게 따로 시키는 방법도 2주차에서 다시 정리한다.

지시문 예시
"우리동네.md를 고쳐 줘. (1) 제목 바로 아래에 세 항목의 목차를 넣고, (2) 세 항목의 핵심 내용을 '항목·내용·출처·기준 시점' 네 열의 표로 정리해서 문서 끝에 붙여 줘. 본문의 수치와 표의 수치가 서로 달라서는 안 돼. 기준 시점을 모르는 항목은 표에 '확인 불가'라고 적어. 고치기 전에 수정 내용을 먼저 제안하고 내 승인을 기다려."

예상되는 에이전트의 행동과 결과. 파일을 읽은 뒤 수정 제안이 비교 화면으로 뜬다. 제목 아래에 목차 세 줄이 초록으로 추가되고, 문서 끝에 표가 초록으로 추가된 모습이 보인다. 승인하면 문서 끝에 대략 다음과 같은 표가 들어간다.

## 요약표

| 항목 | 내용 | 출처 | 기준 시점 |
|------|------|------|------|
| 인구 | 약 ○○만 명, 최근 ... 경향 | ○○구청 통계 페이지 | ○○○○년 ○월 |
| 행정동 수 | ○○개 | ○○구청 행정동 안내 | 확인 불가 |
| 행정 이슈 | ... | ○○신문 기사 | ○○○○년 ○월 |

검증. 두 가지를 본다. (1) 본문의 수치와 표의 수치가 같은가. 에이전트가 표를 만들면서 본문과 다른 값을 적는 일이 실제로 있다. 인구 수치 하나를 골라 본문의 숫자와 표의 숫자를 눈으로 대조한다. (2) 기준 시점 열이 비어 있지 않은가. 비어 있다면 "확인 불가"로 채우라고 지시한 것이 지켜지지 않은 것이다.

에이전트가 틀리는 장면 3: 내가 아는 사실과 다르다

오늘 실습에서 가장 값진 순간은 문서의 어느 문장이 여러분이 아는 사실과 어긋나는 것을 발견할 때다. 가상의 예를 들면 이렇다. 문서에는 구청이 어느 동에 있다고 적혀 있는데 여러분은 구청이 몇 해 전 다른 동으로 옮긴 것을 안다. 행정동 목록에 이미 다른 동과 합쳐져 없어진 옛 동 이름이 남아 있다. 대표 행정 이슈로 적힌 사업이 실은 옆 구의 사업이다. 인구 수치의 기준 시점이 몇 년 전인데 문서는 "최근"이라고 쓰고 있다. 이런 어긋남은 웹에 오래된 페이지가 남아 있거나 이름이 비슷한 지역의 정보가 섞여 들어올 때 생긴다. 잡는 순서는 앞 단계와 같은 네 단계다.

  1. 틀림. 문서가 "○○구청은 ○○동에 있다"고 서술했다.
  2. 검증에서 발견. 여러분은 그 서술이 지금과 다르다는 것을 안다. 이 발견은 링크를 열어 보는 확인과는 종류가 다르다. 출처 페이지가 실제로 그렇게 적혀 있더라도, 그 페이지 자체가 오래되었을 수 있기 때문이다.
  3. 재지시. 무엇이 어떻게 다른지 말하고, 근거를 다시 찾게 한다. "3번 항목의 구청 위치는 내가 알기로 ○○동이야. 다시 확인해서 현재 기준의 근거 페이지 주소를 보여 주고, 확인이 안 되면 그 문장을 '확인 불가'로 바꿔 줘."
  4. 수정 확인. 새로 붙은 출처를 직접 열어 보고, 문서의 서술이 바뀌었는지 본다.

한 가지 주의할 점이 있다. 여러분의 기억도 틀릴 수 있다. 에이전트의 서술과 여러분의 기억이 다를 때 심판은 둘 중 하나가 아니라 공식 출처(구청 누리집, 행정안전부 자료 등)의 현재 페이지다. 재지시의 요지가 "내 말대로 고쳐"가 아니라 "다시 확인해서 근거를 보여 줘"인 이유가 여기 있다. 확인 결과 여러분의 기억이 틀렸다면 그것도 관찰일지에 적을 만한 기록이다. 우연한 발견에 기대지 않고, 아는 사실을 먼저 목록으로 만들어 문서를 시험하는 방법은 2.8에서 한다.

유의 · 출처가 있다고 최신은 아니다
출처 링크가 붙어 있고 그 페이지에 정말 그 내용이 있어도, 그 페이지가 언제 작성되었는지는 별개의 문제다. 검색 결과에는 몇 해 전 페이지가 섞여 있고, 에이전트는 오래된 페이지와 새 페이지를 늘 구별해 주지는 않는다. 그래서 출처를 확인할 때는 "있는가"에 더해 "언제 것인가"를 본다. 지시문에 기준 시점을 적으라고 요구한 것이 바로 이 확인을 위한 장치다.

2.7 같은 주제 두 가지 버전: 검색한 문서와 검색하지 않은 문서

무엇을 왜 하는가. 2.6에서 만든 우리동네.md는 웹을 검색하고 출처를 붙인 문서다. 이번에는 같은 주제로 검색을 금지한 문서를 하나 더 만들어 두 문서를 나란히 놓는다. 목적은 에이전트를 곤경에 빠뜨리는 것이 아니다. 같은 질문에 도구 없이 답할 때 문장이 어떻게 달라지는지를 눈으로 보는 것이다. 두 문서를 대조하면 세 가지가 드러난다. 어느 사실이 두 문서에서 일치하는가, 어느 사실이 어긋나는가, 그리고 출처가 없을 때 문장은 어떤 모습이 되는가. 세 번째가 오늘 가장 값진 관찰이다. 검색 없는 판은 대개 더 매끄럽고 더 자신 있게 읽힌다. 읽기 편한 글과 확인할 수 있는 글이 같지 않다는 사실을 두 파일을 나란히 놓고 확인하게 된다.

검색 없는 판 만들기

지시문 예시
"메모 폴더에 '우리동네_검색없음.md'를 만들어 줘. 주제는 우리동네.md와 같은 ○○시 ○○구야. 이번에는 웹 검색 도구를 쓰지 말고, 우리동네.md도 읽지 말고, 네가 이미 알고 있는 것만으로 같은 세 항목(인구 규모와 최근 증감, 행정동 개수, 대표적인 행정 이슈)을 적어 줘. 항목마다 확신의 정도를 '확실함·비교적 확실함·불확실함' 세 값 중 하나로 표시하고, 아는 것이 없는 항목은 '모름'이라고 적어. 지어내지 마. 문서 맨 위에 '이 문서는 웹 검색 없이 작성되었다'라고 한 줄 적어 줘."

예상되는 에이전트의 행동과 결과. 이 지시의 요점은 도구를 쓰지 않는 것이므로, 대화창에는 검색 기록도 페이지 열람 기록도 없이 파일 쓰기 하나만 나타나야 한다.

문장의 결이 우리동네.md와 다르다는 점을 먼저 본다. "약 ○○만 명이다"가 "대략 ○○만 명 규모로 알고 있다"로 바뀌었고, 주소가 붙던 자리에 확신 표시가 들어갔다. 확신을 표시하라는 요구가 없었다면 두 문서의 문장은 겉보기에 거의 같았을 것이다. 그 점이 중요하다. 검색 없는 판이 검색한 판처럼 보이는 것을 막은 것은 모델이 아니라 지시문에 넣은 한 줄이다.

검증. 도구 사용 기록을 위로 올려 확인한다. 검색이나 페이지 열람 기록이 하나라도 있으면 지시를 어긴 것이다. 우리동네.md를 읽은 기록(Read)이 있어도 마찬가지다. 어겼다면 파일을 지우고 다시 시킨다. 확신 표시가 세 항목 모두에 붙어 있는지, "확실함·비교적 확실함·불확실함·모름" 밖의 표현("어느 정도 확실함" 같은 것)이 섞이지 않았는지도 본다.

두 문서를 나란히 놓기

탐색기에서 우리동네.md를 클릭해 연 뒤, 우리동네_검색없음.md에 마우스 오른쪽 버튼을 눌러 "Open to the Side"를 고른다. 편집기 구역이 좌우로 갈라지면서 두 문서가 나란히 열린다. 열린 파일의 탭을 편집기 오른쪽 가장자리로 끌어다 놓아도 같다. 먼저 눈으로 훑는다. 두 문서에서 같은 항목의 문장을 하나씩 짚어 가며, 숫자가 같은지 다른지를 본다. 그다음 세는 일을 하나 한다. 각 문서에서 출처(주소)가 붙어 있는 문장이 몇 개인지 손으로 세어 종이나 메모에 적는다. 검색본은 대개 세 개 안팎이고 검색 없는 판은 영이다. 두 숫자의 차이가 오늘 두 문서를 만든 이유를 한 줄로 요약해 준다. 이 두 숫자는 과제 1-F에서 다시 쓴다.

그다음 대조를 에이전트에게도 시킨다. 사람의 눈과 에이전트의 정리를 둘 다 만들어 두면, 나중에 둘이 어긋나는 자리에서 무엇이 일어났는지 알 수 있다.

지시문 예시
"메모 폴더의 우리동네.md와 우리동네_검색없음.md를 둘 다 읽고, 세 항목을 '항목·검색본의 서술·검색 없는 판의 서술·두 서술이 일치하는가·검색본의 출처' 다섯 열의 표로 정리해서 메모 폴더에 '버전비교_1주차.md'로 저장해 줘. 두 문서의 문장은 요약하지 말고 원문에서 그대로 옮겨. 일치 여부는 '일치·불일치·비교 불가' 세 값 중 하나로만 적고, 판단이 애매하면 비교 불가로 적은 뒤 왜 애매한지 한 줄 덧붙여. 두 문서에 없는 내용을 새로 채우지 마."

예상되는 에이전트의 행동과 결과. 파일 읽기 두 번과 파일 쓰기 한 번이 기록에 남고, 표가 만들어진다. 표는 다음과 같은 모양이다.

표 1-3. 검색본과 검색 없는 판의 대조 (양식과 채움 예시)

항목 검색본의 서술 검색 없는 판의 서술 일치 여부 검색본의 출처
인구 규모 약 ○○만 명 (○○○○년 ○월 기준) 대략 ○○만 명 규모로 알고 있음 비교 불가 (기준 시점 없음) ○○구청 통계 페이지
행정동 개수 ○○개 ○○개 안팎 불일치 ○○구청 행정동 안내
대표 행정 이슈 ○○ 사업 (○○○○년 기사) ○○ 사업, 진행 상황 모름 일치 ○○신문 기사

표를 읽는 법은 이렇다. 왼쪽 두 열은 확인할 수 있는 서술이고, 셋째 열은 확인할 수 없는 서술이다. 넷째 열의 "불일치"는 검색 없는 판이 틀렸다는 뜻이 아니다. 두 문장이 다르다는 사실만 말한다. 어느 쪽이 맞는지는 다섯째 열의 출처를 직접 열어 봐야 정해진다. 여기서 알 수 있는 것은 검색 없는 판의 문장은 맞든 틀리든 판정할 자리가 없다는 점이다. 다섯째 열에 해당하는 칸이 아예 만들어지지 않기 때문이다.

검증. 세 가지를 확인한다. (1) 표의 둘째와 셋째 열에 적힌 문장을 두 파일에서 찾아 글자 그대로인지 본다. 세 행 중 한 행만 골라도 좋다. 요약되거나 다듬어져 있으면 "원문 그대로 옮겨"라는 지시가 지켜지지 않은 것이다. (2) "일치"로 적힌 행이 있으면 그 행의 숫자를 두 파일에서 눈으로 비교한다. 숫자 한 자리가 다른데도 일치로 적히는 일이 있다. (3) 다섯째 열의 출처 중 하나를 브라우저에서 열어 검색본의 서술이 그 페이지에 정말 있는지 본다. 2.6에서 이미 한 번 한 확인이지만, 대조표를 만든 뒤에 한 번 더 하는 이유는 표 자체가 새로 만들어진 서술이기 때문이다. 원문에서 표로 옮겨지는 사이에도 내용은 바뀔 수 있다.

에이전트가 틀리는 장면 4: 읽지 말라고 한 파일을 읽었다

검색 없는 판을 만들 때 자주 나오는 어긋남이 있다. 두 문서가 지나치게 비슷한 경우다. 숫자까지 똑같고 표현만 조금 다르다면, 에이전트가 우리동네.md를 읽고 참고했을 가능성이 크다. 잡는 순서는 네 단계다.

  1. 틀림. 검색도 파일 읽기도 하지 말라고 했는데, 검색 없는 판의 인구 수치가 검색본과 소수점까지 같다.
  2. 검증에서 발견. 대화를 위로 올려 도구 사용 기록을 확인한다. Read(메모\우리동네.md)가 파일 쓰기 앞에 찍혀 있다. 도구 기록은 에이전트의 보고와 달리 실제로 무슨 도구가 불렸는지를 그대로 보여 준다.
  3. 재지시. 파일을 지우고 다시 시킨다. "우리동네_검색없음.md를 지우고 다시 만들어 줘. 이번에는 메모 폴더의 어떤 파일도 읽지 말고, 웹 검색도 하지 마. 파일을 읽거나 검색해야만 답할 수 있는 항목은 '모름'으로 적어."
  4. 수정 확인. 새로 만들어진 파일의 도구 기록에 읽기와 검색이 없는지 보고, 두 문서의 숫자가 이제 다른지 확인한다.

도구 기록이 깨끗한데도 두 문서의 숫자가 같을 수 있다. 그때는 우연히 같은 값을 말한 것이거나, 검색본의 수치가 이미 널리 알려진 값이었을 것이다. 그 경우에는 문제가 없다. 판정의 근거를 기억이나 인상이 아니라 도구 기록에 두는 것이 이 장면의 핵심이다.

왜 검색 없는 판이 더 잘 읽히는가?
출처를 붙인 문장은 걸리적거린다. 괄호가 들어가고 주소가 붙고 기준 시점이 따라온다. 출처가 없는 문장은 그런 것이 없으니 술술 읽힌다. 문제는 사람이 잘 읽히는 글을 더 믿는 경향이 있다는 점이다. 두 문서를 나란히 놓고 읽어 보면 이 경향이 자기 안에서 작동하는 것을 관찰할 수 있다. 앞으로 에이전트가 만들어 주는 보고서가 매끄럽게 읽힐 때마다 오늘의 이 화면을 떠올리면 된다. 매끄러움은 문장의 성질이고, 확인 가능성은 문서의 구조다. 둘은 따로 논다.

두 문서로 무엇을 할 것인가

대조가 끝나면 검색 없는 판은 버리지 말고 그대로 둔다. 이 파일은 두 곳에서 다시 쓰인다. 바로 다음 단계인 2.8에서는 두 문서의 서술을 여러분이 아는 사실과 함께 놓고 시험한다. 그리고 2주차에는 같은 주제를 검증 손잡이가 달린 지시문으로 다시 시켜, 오늘의 두 판과 셋을 나란히 비교한다. 오늘 만든 파일 셋(우리동네.md, 우리동네_검색없음.md, 버전비교_1주차.md)이 모두 메모 폴더에 있는지 탐색기에서 마지막으로 확인해 둔다.

2.8 내가 아는 사실로 문서를 시험하기: 대조표 만들기

무엇을 왜 하는가. 2.6의 틀리는 장면 3에서는 우연히 눈에 걸린 문장 하나를 잡았다. 우연에 기대지 않는 방법이 대조표다. 순서가 핵심이다. 문서를 먼저 읽고 "어디가 틀렸나" 하고 찾으면 이미 문서의 서술에 끌려간다. 문서가 "구청은 ○○동에 있다"고 적어 두면 읽는 사람의 기억도 슬며시 그쪽으로 기운다. 그래서 내가 아는 사실을 먼저 목록으로 적고, 그다음에 문서의 서술을 그 목록과 맞춘다. 목록이 먼저 있어야 문서가 시험을 받는 쪽이 된다. 이 순서는 오늘의 동네 소개 문서에만 쓰는 요령이 아니다. 뒤에서 데이터를 다룰 때도, 에이전트가 만든 표를 받아들고 "내가 아는 값 몇 개"를 먼저 적은 뒤 표와 맞추는 방식으로 그대로 쓴다.

여러분의 동네는 각자 다르므로 이 절에는 정답표가 없다. 무엇을 아는지도 사람마다 다르다. 그래서 이 절에서 여러분이 채우는 값은 모두 각자의 동네에서 나온다. 아래 예시에 나오는 ○○는 자기 지역의 이름과 숫자로 바꿔 읽으면 된다.

먼저 내가 아는 사실 다섯 가지 적기

이 파일은 손으로 만든다. 2.4에서 익힌 대로 탐색기의 메모 폴더에서 오른쪽 버튼을 눌러 "New File"을 고르고 내가아는사실.md라고 입력한 뒤, 다섯 줄을 직접 친다. 에이전트에게 시키지 않는 이유는 분명하다. 이 목록은 여러분의 머릿속에만 있는 것이어야 시험이 되기 때문이다.

무엇을 적을지 막막하면 다음 종류에서 고른다. 확인할 수 있는 사실이면 무엇이든 좋고, 통계 수치일 필요는 없다. 구청이나 시청이 어느 동에 있는지, 여러분이 사는 동의 이름과 그 옆 동의 이름, 집이나 학교에서 가장 가까운 지하철역이나 버스 종점의 이름, 최근 몇 해 사이에 새로 생겼거나 없어진 시설, 여러분이 다닌 초등학교나 중학교가 어느 동에 있는지 같은 것들이다. 다섯 줄은 이런 모양이 된다.

2. 나는 ○○동에 산다. 옆 동은 ○○동이다.
3. 집에서 가장 가까운 역은 ○○역이다.
4. ○○동의 ○○시장은 몇 해 전에 정비 사업을 했다.
5. 내가 다닌 ○○중학교는 ○○동에 있다.

괄호 안에 그것을 어떻게 아는지를 적어 두면 좋다. 직접 가 본 것, 가족에게 들은 것, 뉴스에서 본 것은 확실함의 정도가 다르다. 나중에 문서의 서술과 어긋났을 때 어느 쪽을 더 의심할지 정하는 데 쓰인다.

문서에서 시험할 서술 다섯 개 뽑기

지시문 예시
"메모 폴더의 우리동네.md를 읽고, 사실 확인이 가능한 서술 다섯 개를 문장 단위로 뽑아 줘. 요약하거나 다듬지 말고 문서에 적힌 문장을 그대로 옮겨. 문장마다 그 문장이 문서의 몇 번째 절에 있는지와 그 문장에 붙은 출처를 함께 적어. 의견이나 평가가 섞인 문장('살기 좋은 동네다' 같은 것)은 빼고, 숫자·이름·위치처럼 맞는지 틀리는지 판정할 수 있는 문장만 골라. 다섯 개가 안 되면 몇 개까지만 가능한지 말해 줘."

예상되는 에이전트의 행동과 결과. 파일 읽기 한 번이 기록에 남고 대화창에 목록이 나온다. 파일은 아직 만들지 않는다.

● 우리동네.md에서 판정 가능한 서술 5개를 뽑았습니다.
  1. (1절) "○○구의 주민등록 인구는 약 ○○만 명이다." 출처: ○○구청 통계 페이지
  2. (1절) "최근 3년간 인구가 줄어드는 경향을 보인다." 출처: ○○구청 통계 페이지
  3. (2절) "○○구는 ○○개의 행정동으로 이루어져 있다." 출처: ○○구청 행정동 안내
  4. (3절) "○○ 사업이 ○○동 일대에서 추진되고 있다." 출처: ○○신문 기사
  5. (3절) "○○구청은 ○○동에 있다." 출처: 없음

다섯째 줄처럼 출처가 없는 문장이 섞여 나오는 일이 흔하다. 2.6에서 항목마다 출처를 붙이라고 했지만, 그 요구는 세 항목의 본문에 걸린 것이고 문장 하나하나에 걸린 것은 아니었다. 지시의 범위가 어디까지였는지를 되짚어 볼 만한 대목이다. 출처 없는 문장은 지우지 말고 그대로 둔다. 대조표에서 가장 먼저 확인할 행이 된다.

검증. 뽑힌 다섯 문장을 우리동네.md에서 하나씩 찾아 글자 그대로인지 확인한다. 편집기에서 Ctrl+F를 눌러 문장의 앞 대여섯 글자를 붙여 넣으면 바로 찾을 수 있다. 문장이 다듬어져 있거나 두 문장이 하나로 합쳐져 있으면 "원문 그대로 옮기라"는 지시가 지켜지지 않은 것이다. 다시 뽑게 한다. 여기서 문장이 조금이라도 바뀌면 뒤의 판정이 전부 헛돈다. 여러분이 판정하는 대상은 문서의 문장이지 에이전트가 요약한 문장이 아니기 때문이다.

대조표 만들기

지시문 예시
"메모 폴더에 '대조표_1주차.md'를 만들어 줘. 방금 뽑은 다섯 문장을 행으로 하고, 열은 '번호·문서의 서술·내가 아는 사실·판정·근거 페이지' 다섯 개야. '문서의 서술' 열에는 뽑은 문장을 그대로 넣고, '근거 페이지' 열에는 그 문장에 붙어 있던 출처 주소를 넣어. 출처가 없으면 '없음'이라고 적어. '내가 아는 사실'과 '판정' 열은 내가 손으로 채울 거니까 비워 둬. 표 아래에 '판정은 맞음·틀림·모름 세 값 중 하나로만 적는다'라고 안내 한 줄을 넣어 줘."

예상되는 에이전트의 행동과 결과. 파일 쓰기 하나가 기록에 남고, 메모 폴더에 표가 든 파일이 생긴다. 표는 다음과 같은 양식이다.

표 1-4. 내가 아는 사실과 문서의 서술 대조표 (양식)

번호 문서의 서술 내가 아는 사실 판정 근거 페이지
1 "○○구의 주민등록 인구는 약 ○○만 명이다." (내가아는사실.md에 해당 항목 없음) 모름 ○○구청 통계 페이지

표를 읽는 법은 이렇다. 셋째 열이 비어 있는 행은 여러분이 판정할 근거가 없는 행이고, 그런 행의 판정은 "모름"이다. 셋째 열에 여러분의 항목이 들어간 행만 "맞음" 또는 "틀림"이 될 수 있다. 위의 채움 예시에서는 다섯 행 중 셋이 "모름"이다. 이것은 흔한 결과이고 실패가 아니다. "모름"의 행들은 여러분이 확인할 수 없는 서술이 문서에 얼마나 들어 있는지를 세어 준다. 다섯 중 셋이 모름이라면, 이 문서에서 여러분 힘으로 지킬 수 있는 부분은 다섯 중 둘뿐이라는 뜻이다. 나머지 셋을 지키는 방법이 출처를 열어 보는 확인이고, 그래서 다섯째 열이 함께 있다.

여기서 알 수 있는 것이 하나 더 있다. 5번 행처럼 근거 페이지가 "없음"이면서 판정이 "틀림"인 행이 가장 나쁜 조합이다. 문장은 단정적인데 확인할 자리도 없고 실제로 틀리기까지 했다. 반대로 4번 행은 근거 페이지가 있으므로, 여러분과 문서 중 어느 쪽이 맞는지 지금 바로 열어 볼 수 있다.

검증. 표가 만들어지면 채우기 전에 두 가지를 먼저 확인한다. (1) 둘째 열의 다섯 문장이 앞 단계에서 뽑은 문장과 같은가. 파일로 옮겨 적는 사이에 문장이 다시 다듬어지는 일이 있다. (2) 다섯째 열의 주소가 우리동네.md에 적힌 주소와 같은가. 한 행만 골라 두 파일을 나란히 놓고 주소를 글자 단위로 비교한다. 이 두 가지가 맞으면 이제 셋째 열과 넷째 열을 손으로 채운다. 채울 때 내가아는사실.md의 몇 번 항목을 근거로 삼았는지를 셋째 열에 함께 적어 두면, 나중에 표만 보고도 판정의 출처를 알 수 있다.

틀린 서술 고치게 하기

판정이 "틀림"인 행이 나왔다면 그 행이 오늘 실습의 수확이다. 이제 그 문장을 고치게 한다. 고칠 때 지켜야 할 것이 두 가지 있다. 첫째, 틀렸다고 지목한 문장만 고쳐야 한다. 둘째, 고친 문장에는 새 근거가 붙어야 한다.

지시문 예시
"대조표_1주차.md에서 판정이 '틀림'인 행은 4번과 5번이야. 우리동네.md의 그 두 문장을 다시 확인해 줘. 내 말을 근거로 고치지 말고, 구청 누리집 같은 공식 페이지에서 현재 기준의 근거를 찾아서 고쳐. 고친 문장마다 근거 페이지 주소와 그 페이지에 적힌 갱신 날짜를 함께 적어. 근거를 못 찾으면 문장을 지우지 말고 문장 끝에 '(확인 불가)'만 붙여. 4번과 5번 외의 문장은 한 글자도 바꾸지 마."

예상되는 에이전트의 행동과 결과. 검색과 페이지 열람이 몇 차례 기록에 남은 뒤 수정 제안이 비교 화면으로 뜬다. 두 문장이 붉은색으로 지워지고 새 문장이 초록색으로 들어가는 모양이다.

- ○○구청은 ○○동에 있다.
+ ○○구청은 ○○동에 있다(○○구청 누리집 오시는 길, ○○○○년 ○월 갱신).
  https://...

검증. 승인하기 전에 비교 화면부터 읽는다. 붉은 줄과 초록 줄이 4번과 5번 문장에만 걸려 있는가. 다른 절의 문장이 함께 바뀌고 있다면 거부하고 다시 시킨다. 승인한 뒤에는 새로 붙은 근거 페이지를 브라우저에서 직접 연다. 그 페이지에 정말 그 내용이 있는지, 갱신 날짜가 문서에 적힌 것과 같은지 본다. 마지막으로 대조표_1주차.md로 돌아가 4번과 5번 행의 판정을 다시 채운다. 문서가 고쳐졌으므로 이제 "맞음"이 되어야 한다. 여전히 "틀림"이면 고치는 작업이 실패한 것이다.

에이전트가 틀리는 장면 5: 지적하면 근거 없이 사과하고 바꾼다

틀렸다고 말했을 때 에이전트가 보이는 반응 중에 조심해야 할 것이 있다. 확인하지 않고 사과부터 한 다음 여러분의 말을 그대로 문서에 옮겨 적는 반응이다.

  1. 틀림. "죄송합니다. 말씀하신 대로 수정했습니다"라는 보고와 함께 문서의 문장이 여러분이 말한 내용으로 바뀌었다. 그런데 도구 사용 기록에는 검색도 페이지 열람도 없다. 근거를 찾은 적이 없다는 뜻이다.
  2. 검증에서 발견. 고친 문장 뒤에 붙은 출처를 본다. 주소가 없거나, 고치기 전과 같은 주소가 그대로 붙어 있다. 같은 주소가 붙어 있다면 그 페이지를 열어 본다. 새 문장의 내용은 그 페이지에 없을 것이다.
  3. 재지시. 근거의 출처를 분명히 지정해 다시 시킨다. "내 말은 근거가 아니야. 공식 페이지에서 확인한 뒤 그 페이지 주소를 붙여 줘. 확인이 안 되면 내 말도 반영하지 말고 문장 끝에 '(확인 불가)'만 붙여."
  4. 수정 확인. 도구 사용 기록에 검색과 페이지 열람이 새로 생겼는지 보고, 붙은 주소를 직접 연다.

이 장면이 중요한 이유는 결과가 우연히 맞을 수도 있기 때문이다. 여러분의 기억이 옳았다면 문서는 결과적으로 바르게 고쳐진다. 그러나 그것은 확인을 거쳐 바르게 된 것이 아니라 여러분의 말을 옮겨 적어 우연히 바르게 된 것이다. 다음번에 여러분의 기억이 틀렸을 때는 그대로 틀린 문장이 들어간다. 2.6에서 말한 것처럼 심판은 여러분도 에이전트도 아니고 공식 출처의 현재 페이지다. 그래서 재지시의 요지는 언제나 "내 말대로 고쳐"가 아니라 "다시 확인해서 근거를 보여 줘"가 된다.

검색 없는 판에도 같은 시험을

시간이 남으면 같은 다섯 문장으로 우리동네_검색없음.md도 시험해 본다. 문서가 다르므로 문장을 새로 뽑아야 하지만, 여러분의 내가아는사실.md는 그대로 쓴다. 결과는 대체로 이렇게 갈린다. 검색 없는 판에서는 판정이 "모름"인 행이 줄고 "맞음"과 "틀림"이 늘어난다. 문장이 흐릿하게 쓰여 있어 판정하기 쉬운 것들만 남기 때문이다. 그러나 판정이 "틀림"인 행에서 고칠 근거를 찾을 자리가 없다. 다섯째 열이 통째로 "없음"이기 때문이다. 두 문서의 대조표를 나란히 놓으면 표 1-3에서 본 차이가 다른 각도에서 한 번 더 보인다.

왜 다섯 개인가?
문서의 모든 문장을 다 확인할 수는 없다. 그래서 몇 개를 골라 본다. 이렇게 일부를 골라 전체를 가늠하는 것을 표본이라 하고, 앞으로 데이터를 다룰 때 계속 쓰게 될 말이다. 다섯이라는 수에 특별한 근거는 없다. 수업 시간 안에 손으로 확인할 수 있는 정도라서 다섯으로 잡았다. 중요한 것은 수가 아니라 표본을 읽는 방식이다. 다섯 중 하나가 틀렸다면 나머지 문장도 같은 비율로 틀렸을 수 있다고 보는 것이 맞다. 다섯이 모두 맞았다고 해서 문서 전체가 맞는다고 말할 수는 없다. 표본 확인은 "이 문서가 옳다"를 증명하지 않고 "이 문서를 어느 정도로 믿을지"를 조정해 준다. 이것이 세 겹 검증의 세 번째인 사람의 눈이 하는 일이고, 앞의 두 겹(지시문에 확인 장치를 달기, 검증을 따로 시키기)은 2주차에서 이름과 함께 배운다.

2.9 무엇이 되고 무엇이 안 되나: 첫 한계 관찰

무엇을 왜 하는가. 마지막으로, 에이전트의 한계를 일부러 건드려 본다. 다섯 가지 시험을 한다. 각 시험에서 볼 것은 "된다, 안 된다"만이 아니다. 더 중요한 것은 그 답을 여러분이 확인할 수 있는가다. 답이 나왔는데 어디서 온 것인지 알 수 없다면, 그 답은 맞더라도 쓸 수 없다. 이 관점이 2주차의 주제(검증 가능성)로 이어진다. 시험 1과 2는 지시문 없이 대화창에서 바로 하고, 시험 3-5는 아래 지시문을 차례로 입력한다.

시험 1. 방금 대화의 기억. 패널의 새 대화 버튼을 눌러 새 대화를 연 뒤 "아까 만든 문서 제목이 뭐였지?"라고 물어보라. 에이전트는 이전 대화의 내용을 기억하지 못한다. 다만 폴더의 파일을 읽어 보고 답할 수는 있다. "폴더를 살펴봐도 돼"라고 덧붙이면 메모 폴더의 우리동네.md를 열어 제목을 찾아낼 것이다. 기억(대화)과 기록(파일)의 차이를 관찰하라. 이 차이는 2주차 1회차(맥락창)에서 원리로 설명된다. 시험이 끝나면 이전 대화 목록에서 원래 대화로 돌아갈 수 있다.

시험 2. 한국어 고정. 에이전트가 영어로 답하는 순간이 있었다면 "앞으로 이 폴더에서는 항상 한국어로 답해 줘"라고 지시해 보라. 그 대화 안에서는 지켜지지만, 새 대화에서는 다시 잊힌다. 매번 말하지 않고 영구히 고정하는 방법(CLAUDE.md)은 2주차에서 배운다.

지시문 예시
시험 3: "오늘 우리 학교가 있는 도시의 날씨를 알려 줘. 답을 어디서 가져왔는지도 함께 말해 줘."

시험 4: "data 폴더의 인구현황.csv를 열어서 첫 다섯 줄을 보여 줘."

시험 5: "1부터 99까지 홀수의 제곱을 모두 더하면 얼마야? 먼저 코드를 쓰지 말고 답하고, 그다음 코드를 실행해서 다시 답해 줘. 두 답이 다르면 어느 쪽을 믿어야 하는지도 말해 줘."

예상되는 에이전트의 행동과 결과. 시험마다 결과의 갈래가 둘 이상이다. 어느 갈래가 나오든 관찰 대상이다.

시험 3(오늘 날씨)에서 에이전트는 스스로 날씨를 알지 못한다. 에이전트의 두뇌인 언어모델은 정해진 시점까지의 자료로 만들어졌고 지금 창밖을 볼 수 없기 때문이다. 그래서 갈래가 둘로 나뉜다. 하나는 "실시간 정보는 알 수 없다"고 답하는 것이고, 다른 하나는 웹 검색 도구를 써서 일기예보 페이지를 열고 그 내용을 알려 주는 것이다. 후자라면 패널의 도구 사용 기록에 검색과 페이지 열람이 남는다. 반대로 검색 기록 없이 날씨를 단정하는 답이 나왔다면, 그것은 확인할 수 없는 답이다.

시험 4(없는 파일)에서 data 폴더는 비어 있다. 정상적인 답은 "그런 파일이 없다"이다. 파일을 찾는 명령을 실행하고 없다고 보고하거나, 폴더 목록을 보여 주며 어떤 파일을 뜻하는지 되묻는 것이 좋은 반응이다. 이따금 에이전트가 파일 이름만 보고 "시군구별 인구 데이터로 보입니다" 같은 설명을 시작하거나, 묻지 않은 예시 파일을 만들어 주겠다고 나서는 경우가 있다. 이것이 오늘 관찰하는 마지막 틀리는 장면이다. 여러분은 data 폴더가 비어 있다는 사실을 탐색기로 알고 있으므로 즉시 잡을 수 있다. "없는 파일을 있는 것처럼 말하지 마. 없으면 없다고 답해"라고 재지시하고 답이 바뀌는지 본다.

시험 5(긴 계산)에서는 두 답을 받는다. 코드 없이 답한 값과 코드를 실행해 얻은 값이다. 정답은 166,650이다. 코드로 계산한 답은 코드와 실행 결과가 기록으로 남아 누구든 다시 돌려 확인할 수 있지만, 머릿속으로 답한 값은 맞더라도 확인할 길이 없다. 두 답이 같았다면 "이번에는 맞았다"는 것이고, 달랐다면 어느 쪽을 믿을지에 대한 에이전트의 설명이 "코드 쪽"인지 본다. 코드를 실행하는 장면은 대략 다음과 같다.

● 먼저 계산해 보면 166,650입니다.
● 코드로 확인하겠습니다.
  Bash(python -c "print(sum(k*k for k in range(1, 100, 2)))")   ← 승인 요청
  166650
● 두 답이 같습니다. 다르다면 실행 결과를 믿어야 합니다.
  실행 결과는 코드가 남아 있어 다시 확인할 수 있기 때문입니다.

검증. 시험별로 확인할 것이 다르다. 시험 3은 도구 사용 기록에 검색이 있는가, 답에 출처와 시각이 있는가를 본다. 시험 4는 탐색기의 data 폴더가 비어 있음을 여러분이 알고 있으므로, 에이전트의 답이 그 사실과 맞는가를 본다. 시험 5는 코드가 실제로 실행되었는지 터미널 또는 도구 기록에서 확인하고, 두 답이 다르다면 코드 답을 기준으로 삼는다. 다섯 시험의 결과를 표 1-5의 형식으로 정리해 두자. 오른쪽 두 열은 각자의 화면에서 관찰한 대로 채운다.

2.10 선택 심화: 관찰 일지 양식과 대화 기록 정리

무엇을 왜 하는가. 오늘 관찰한 것을 머리에만 두면 다음 주에 사라진다. 시험 1에서 보았듯 에이전트도 대화를 잊지만, 사람도 잊는다. 그래서 관찰을 파일로 남기는 양식을 하나 만들어 둔다. 이 양식은 2주차 실습의 관찰 일지 단계에서 그대로 이어 쓴다. 수업 시간에 못 해도 좋고, 과제 1-B를 할 때 함께 하면 된다.

지시문 예시
"메모 폴더에 '관찰일지_양식.md'를 만들어 줘. 기록 하나마다 다음 여섯 항목을 적는 양식이야. 날짜, 시킨 일(지시문 원문), 에이전트가 한 일(사용한 도구의 순서), 결과가 맞았는가(무엇으로 확인했는가), 틀렸다면 어떻게 잡았는가, 다음에 바꿔 볼 것. 그다음 이 양식을 복사해서 '관찰일지_1주차.md'를 만들고, 오늘 우리동네.md를 만들 때의 작업을 첫 기록으로 채워 줘. 기록의 내용은 네가 기억하는 대로가 아니라 이 대화의 도구 사용 기록과 파일에서 확인한 사실만 적고, 확인이 안 되는 칸은 비워 둬."

예상되는 에이전트의 행동과 결과. 파일 두 개를 만들겠다는 승인 요청이 차례로 온다. 양식 파일은 대략 다음과 같은 모양이다.

# 관찰 일지

## 기록 1
- 날짜:
- 시킨 일(지시문 원문):
- 에이전트가 한 일(사용한 도구의 순서):
- 결과가 맞았는가(무엇으로 확인했는가):
- 틀렸다면 어떻게 잡았는가:
- 다음에 바꿔 볼 것:

관찰일지_1주차.md에는 같은 틀에 오늘 우리동네.md 작업이 채워진다. "에이전트가 한 일" 칸에는 웹 검색 몇 회, 페이지 열람 몇 회, 파일 쓰기 한 회 같은 도구 순서가, "결과가 맞았는가" 칸에는 여러분이 링크를 열어 대조한 사실이 들어가야 한다. 다만 에이전트는 여러분이 브라우저에서 무엇을 확인했는지 알지 못하므로 그 칸은 비어 있을 것이다. 여러분이 직접 채운다.

검증. 세 가지를 본다. (1) 탐색기의 메모 폴더에 두 파일이 있고 여섯 항목이 지시한 순서대로 들어 있는가. (2) 관찰일지_1주차.md의 "에이전트가 한 일" 칸을 패널의 도구 사용 기록과 대조해 본다. 검색 횟수나 순서가 실제 기록과 다르면 고쳐 쓴다. 에이전트가 자기 행동을 요약할 때도 실제 기록과 어긋날 수 있다. (3) "결과가 맞았는가" 칸에 "확인했음"이 아니라 무엇으로 확인했는지(어느 링크를 열어 어느 수치를 대조했는지)가 적혀 있는가.

대화 기록을 메모로 남기기

관찰일지가 "무엇을 배웠는가"의 기록이라면, 대화 기록은 "무엇을 시켰는가"의 기록이다. 오늘 입력한 지시문은 2주차부터 고쳐 쓰고 다시 쓰게 되므로, 흩어진 대화창에서 꺼내 파일 하나로 모아 둔다. 오늘은 새 대화를 여러 번 열었으므로 대화마다 따로 시키거나, 이전 대화 목록에서 그 대화로 돌아가 시킨다.

지시문 예시
"이 대화에서 내가 입력한 지시문을 처음부터 순서대로 모아서 메모 폴더에 '대화기록_1주차.md'로 저장해 줘. 지시문마다 (1) 지시문 원문, (2) 네가 사용한 도구를 순서대로 한 줄, (3) 만들거나 고친 파일의 경로를 적어. 지시문을 요약하거나 고쳐 쓰지 말고 원문 그대로 옮겨. 이 대화에서 확인할 수 없는 것은 적지 마. 파일이 이미 있으면 덮어쓰지 말고 뒤에 이어 붙여."

예상되는 에이전트의 행동과 결과. 도구 기록에는 파일 쓰기 하나(이미 있으면 읽기와 고치기)만 남는다. 만들어진 파일은 대략 다음과 같은 모양이다.

에이전트가 영어로 답한다 첫 대화의 기본 언어 설정 "한국어로 답해 줘"라고 지시 (2주차에서 영구 고정법을 배움)
"폴더를 신뢰하느냐"는 물음이 계속 나온다 매번 다른 폴더를 열고 있음 항상 같은 공공데이터분석 폴더를 열 것
파일이 만들어졌다는데 탐색기에 안 보인다 다른 폴더에 만들어졌거나 새로고침 필요 에이전트에게 "방금 만든 파일의 전체 경로를 알려 줘"라고 확인. 탐색기 위쪽의 새로고침 아이콘을 누른다
승인을 눌렀는데 아무 일도 안 일어나는 것 같다 명령이 터미널에서 실행 중이거나 웹 검색이 오래 걸리는 중 패널의 진행 표시를 보며 기다린다. View → Terminal로 터미널을 열어 무엇이 돌고 있는지 본다
비교 화면이 뜨지 않고 파일이 바로 바뀌었다 새 파일을 만들 때는 비교할 이전 내용이 없어 비교 화면이 없다. 기존 파일인데도 묻지 않고 바뀐다면 승인 설정이 바뀐 것 새 파일이면 정상. 기존 파일이 묻지 않고 바뀐다면 2주차의 권한 모드 설명을 참고해 설정을 확인
터미널 출력의 한글이 물음표나 네모로 깨져 보인다 터미널의 문자 인코딩이 한글과 맞지 않음 에이전트에게 "터미널 출력 인코딩을 UTF-8로 맞춰 줘"라고 지시하거나, 결과를 파일로 저장하게 해서 편집기에서 확인
우리동네.md의 검색이 계속 실패하거나 검색을 하지 않는다 웹 검색 승인을 거부했거나 네트워크 문제 승인 요청을 다시 읽고 승인. 그래도 안 되면 "검색이 안 되면 그 항목을 확인 불가로 적어 줘"라고 지시해 문서를 일단 완성
규칙을 정해 줬는데 두세 번째 지시부터 무시한다 대화가 길어지면 앞서 말한 내용이 뒤로 밀린다 (2주차 맥락창에서 원리를 배움) 어긴 규칙의 번호를 짚어 재지시. 영구 고정은 2주차의 CLAUDE.md
에이전트가 파일을 지우겠다는 승인을 요청한다 옮기기·정리 작업에 삭제가 따라온다 대상 파일의 이름과 폴더를 읽고, 내가 시킨 바로 그 파일일 때만 승인. 여러 파일을 한꺼번에 지우는 명령(별표 *가 든 명령)은 거부하고 하나씩 시킨다
"검색하지 말라"고 했는데 검색 도구를 쓴다 지시의 제약 부분을 놓침 승인 요청을 거부하고 "웹 검색 도구를 쓰지 말고 아는 것만으로 써 줘"라고 재지시. 도구 기록에 검색이 없는지 확인
대조표의 판정이 "대체로 일치"처럼 정해 준 세 값을 벗어난다 형식 제약이 느슨하게 해석됨 표마다 정한 세 값을 그대로 다시 말해 준다. 버전비교표는 "일치·불일치·비교 불가", 대조표는 "맞음·틀림·모름"이다. "판정은 이 세 값 중 하나로만 다시 적어 줘"라고 재지시
두 문서를 나란히 놓고 비교할 수 없다 편집기 분할을 모름 탐색기에서 파일에 오른쪽 버튼 → "Open to the Side", 또는 열린 파일의 탭을 편집기 오른쪽 가장자리로 끌어다 놓기
규칙을 정리만 하라고 했는데 파일을 만들어 버린다 지시의 금지 부분("지금은 파일을 만들지 말고")을 놓침 승인 요청 단계에서 거부한다. 이미 만들어졌으면 지우지 말고 어느 폴더에 생겼는지 적어 둔 뒤 규칙 실험의 관찰 자료로 쓴다
파일은 제자리에 만들었는데 경로 한 줄이 계속 빠진다 형식에 관한 규칙은 위치에 관한 규칙보다 먼저 잊힌다 "방금 만든 파일의 전체 경로를 규칙 4대로 한 줄 적어 줘"라고 그때마다 재지시. 반복되는 것이 정상이며, 이것이 2주차에 CLAUDE.md를 쓰는 이유다
검색 없는 판이 검색본과 숫자까지 똑같다 우리동네.md를 읽고 참고했을 수 있음 도구 사용 기록에 Read(우리동네.md)가 있는지 확인. 있으면 파일을 지우고 "메모 폴더의 어떤 파일도 읽지 마"를 넣어 다시 지시
문서에서 뽑았다는 다섯 문장이 문서에 그대로 없다 옮기는 과정에서 요약되거나 두 문장이 합쳐짐 편집기에서 Ctrl+F로 문장 앞 대여섯 글자를 찾아 대조. 다르면 "문서의 문장을 글자 그대로 옮겨 줘"라고 다시 시킨다
틀렸다고 말하자마자 사과하고 고쳐 버린다 확인 없이 사용자의 말을 근거로 삼음 도구 사용 기록에 검색·페이지 열람이 새로 생겼는지 확인. 없으면 "내 말은 근거가 아니야. 공식 페이지에서 확인하고 주소를 붙여 줘"라고 재지시

제출 과제

과제 1-A. 우리 동네 소개 문서 완성. 2.6절의 우리동네.md를 2판(목차와 요약표 포함)까지 완성해 제출한다. 평가 기준은 문서의 화려함이 아니라 (1) 모든 항목에 출처와 기준 시점이 있는가, (2) 출처와 본문 수치가 일치하는가, (3) 본문과 요약표의 수치가 일치하는가이다.

과제 1-B. 첫 관찰 기록. 메모 폴더에 '관찰일지_1주차.md'를 만들고(직접 타이핑해도, 2.10절처럼 에이전트에게 받아 적게 해도 좋다) 다음 세 가지를 적는다. (1) 에이전트가 기대보다 잘한 것 한 가지, (2) 기대보다 못한 것 한 가지, (3) 다음에 시켜 보고 싶은 것 한 가지. 2.10절의 양식을 썼다면 여섯 항목 기록 하나를 더한다. 평가 기준은 "확인했음"이 아니라 무엇으로 확인했는지가 적혀 있는가다.

과제 1-C. 되는 것과 안 되는 것. 표 1-5를 각자의 화면에서 관찰한 결과로 다시 채우고, 여섯 번째 시험을 하나 직접 설계해 추가한다(예: 오늘 날짜 묻기, 어제 만든 파일 찾게 하기, 긴 문서 요약시키기). 여섯 행마다 "관찰 포인트" 열에 그 답을 무엇으로 확인할 수 있는지를 적는다. 평가 기준은 시험의 독창성이 아니라, 각 행의 관찰 포인트가 "확인 가능한가"의 관점으로 적혀 있는가이다.

과제 1-D. 규칙 실험 보고. 2.5절의 실험 결과를 표로 정리해 제출한다. 행은 세 갈래(같은 대화의 바로 다음 지시, 몇 번의 지시 뒤, 새 대화), 열은 네 규칙이다. 칸마다 지켜졌는지 여부와 그것을 무엇으로 확인했는지(탐색기에서 본 폴더와 파일 이름, 보고의 마지막 줄)를 적는다. 평가 기준은 각 칸의 확인 방법이 구체적인가이다. 2주차에 CLAUDE.md를 만든 뒤 같은 표를 다시 채워 비교하게 되므로, 새 대화에서 규칙을 어기고 만들어진 파일은 지우지 말고 둔다.

과제 1-E. 대조표. 2.8절의 내가아는사실.md와 대조표_1주차.md를 제출한다. 대조표의 "틀림" 행에는 근거 페이지를 직접 열어 여러분과 에이전트 중 누가 맞았는지 한 줄을 덧붙인다. "틀림"이 한 행도 없었다면 "모름" 행 하나를 골라 출처를 직접 열어 확인한 결과를 같은 형식으로 덧붙인다. 평가 기준은 (1) 다섯 행 모두에 근거 페이지 주소가 있거나 "없음"으로 적혀 있는가, (2) 판정이 "틀림"인 행의 판정을 직접 확인했는가이다.

과제 1-F. 두 버전 비교 보고. 2.7절의 우리동네_검색없음.md와 버전비교_1주차.md를 제출하고, 버전비교_1주차.md 아래에 여러분이 직접 센 숫자 세 개를 덧붙인다. (1) 검색본에서 출처가 붙은 문장의 수, (2) 검색 없는 판에서 출처가 붙은 문장의 수, (3) 두 문서에서 같은 항목의 숫자가 서로 다른 항목의 수다. 세 숫자 아래에 두 문서 중 어느 쪽을 다른 사람에게 보여 줄 수 있겠는지와 그 이유를 세 문장 안으로 적는다. 평가 기준은 결론이 아니라, 세 숫자가 두 파일에서 실제로 세어 나온 값인가이다. 문장 수를 셀 때는 문서를 나란히 열어 두고 눈으로 세며, 에이전트에게 세게 하지 않는다.
